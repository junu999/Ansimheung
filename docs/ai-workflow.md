# AI로 개발할 때 팀 규칙

> AI 도구(Claude Code, Cursor, ChatGPT, Copilot 등)는 자유롭게 써도 됩니다. 대신 **AI가 쓴 코드도 PR을 올린 사람의 코드**입니다.
> AI에게 줄 규칙은 [AGENTS.md](../AGENTS.md), 정책·알고리즘은 [domain.md](domain.md), API는 [api.md](api.md).

## 1. 원칙 다섯 가지

1. **이해 못 한 코드는 올리지 않는다.** 리뷰어가 "이 줄 왜 있어요?"라고 물으면 올린 사람이 답할 수 있어야 한다. 발표·질의응답에서도 우리가 설명해야 한다.
2. **이슈 하나만 맡긴다.** "제보 기능 다 만들어줘" ❌ → "#11 완료 기준대로 `POST /api/reports`만" ⭕. 범위가 넓으면 AI가 명세에 없는 기능과 파일을 마구 만든다.
3. **정답은 문서와 mock JSON.** AI가 그럴듯한 필드명·enum·숫자를 지어내면 그건 버그다. 문서에 없으면 추측하지 말고 팀 채팅에 묻는다.
4. **테스트로 확인한다.** AI가 "테스트 통과했어요"라고 해도 직접 `./gradlew test`를 돌린다.
5. **비밀값·개인정보를 AI에 붙여 넣지 않는다.** DB 비밀번호, 실제 학부모 연락처, 현장 사진 원본(얼굴·번호판) 등.

## 2. 작업 순서

```
이슈 고르기 → develop 최신화 → feature 브랜치 → AI에게 "계획 먼저" → 계획 확인 → 구현 → 직접 테스트·실행
→ 스스로 diff 읽기 → PR (템플릿의 AI 사용 칸) → 리뷰 1명 → Squash merge → 노션·이슈 정리
```

```bash
git switch develop && git pull
git switch -c feature/F-RPT-03-report-api
docker compose up -d
```

## 3. 프롬프트 템플릿

### 3-1. 기능 구현 (가장 많이 씀)

```
이 저장소의 AGENTS.md 규칙을 따라줘.
GitHub 이슈 #11 "[F-RPT-03] 제보 등록 API (새 지점)"을 구현할 거야.

[이슈 본문 붙여넣기 — 할 일 / 완료 기준]

참고: docs/api.md 의 POST /api/reports, docs/domain.md 의 P-04·P-05·V-06~V-09,
응답 모양은 src/main/resources/static/mock/reports-created.json 과 같아야 해.

먼저 코드를 쓰지 말고 ① 만들거나 고칠 파일 목록 ② 각 파일에서 할 일 ③ 테스트 목록을 보여줘.
명세에 없는 부분이 있으면 추측하지 말고 질문으로 정리해 줘.
```

계획을 확인한 뒤: `좋아, 계획대로 구현하고 테스트도 작성해줘. 새 라이브러리는 추가하지 마.`

### 3-2. 테스트 먼저 (알고리즘·계산)

```
docs/domain.md 6장 "테스트 기대값" 표를 그대로 JUnit 테스트로 만들어줘 (RiskCalculatorTest).
아직 구현은 하지 말고 테스트만. 계수는 HazardType/HazardStatus enum과 AnsimheungProperties에서 읽는다고 가정해.
```

### 3-3. 프론트 화면

```
AGENTS.md 프론트 규칙대로, static/js/app.js 의 경로 비교 화면에서 [바꿀 것]을 해줘.
서버 호출은 js/api.js 메서드만 쓰고, 필드 변환이 필요하면 js/mappers.js 에 추가하고
src/test/js/mappers.test.mjs 에 테스트를 붙여줘. 디자인(css 클래스)은 기존 것을 재사용해.
```

### 3-4. 오류 해결

```
이 오류가 나. 원인 후보를 가능성 높은 순으로 3개 말해주고, 각각 확인하는 방법을 알려줘.
코드를 고치기 전에 원인부터 확인하자.
[오류 전문 + 실행한 명령 + 관련 파일]
```
README의 "자주 막히는 곳" 표에 이미 답이 있는지 먼저 본다.

### 3-5. 내 PR 셀프 리뷰

```
develop 대비 이 브랜치의 변경(git diff develop...HEAD)을 AGENTS.md 기준으로 리뷰해줘.
특히 ① 하드코딩된 정책값 ② mock JSON과 다른 응답 필드 ③ 출발지 좌표 로그 ④ 빠진 테스트
⑤ 이슈 범위 밖 변경을 찾아줘. 고치지는 말고 목록만.
```

## 4. 리뷰 체크리스트 (리뷰어용)

AI가 쓴 코드에서 특히 자주 나오는 문제들:

- [ ] 이슈 범위 밖 파일·기능이 섞여 있지 않은가 (특히 "덤으로" 만든 유틸·설정)
- [ ] 필드명·enum·URL이 [api.md](api.md)·mock JSON과 정확히 같은가 (`fromLat` vs `lat`, `empathyCount` vs `likes`)
- [ ] 20·25·50·500·λ 같은 숫자가 코드에 직접 박혀 있지 않은가
- [ ] 오류를 `ApiException(ErrorCode.X)`로 던지는가 (직접 `ResponseEntity.status(400)` ❌)
- [ ] `catch (Exception e)`로 오류를 삼키지 않는가
- [ ] 좌표 순서 (GeoJSON `[lng,lat]` / Leaflet `[lat,lng]`)
- [ ] 출발지 좌표·비밀번호·세션이 로그에 찍히지 않는가 (`log.info(request)` 통째로 찍기 주의)
- [ ] 테스트가 실제로 의미 있는 값을 검사하는가 (`assertNotNull`만 있는 테스트 ❌)
- [ ] 마이그레이션 V1 수정, 새 의존성 추가가 없는가
- [ ] 프론트: `fetch` 직접 호출, `innerHTML`에 이스케이프 안 된 서버 문자열이 없는가

## 5. AI가 문서와 다른 걸 제안할 때

AI가 "이 설계가 더 낫다"고 하는 경우(예: JWT, 경로 캐시, 반경 합산)가 많다. 대부분 이미 팀에서 **이유가 있어서 정한 것**이다 ([domain.md](domain.md)에 이유 있음).
바꾸고 싶으면 코드에 바로 넣지 말고 팀 채팅이나 이슈에 제안 → 합의되면 문서부터 고친다.

## 6. 제출물에서의 AI 사용 표기

- 과제의 AI 사용 규정(허용 범위·표기 방법)은 **담당 교수님 공지를 따른다** — 확인 후 이 절을 채울 것.
- 확인 전 기본값: 최종 보고서에 "개발 과정에서 AI 코딩 도구를 보조로 사용했고, 모든 코드는 팀원이 검토·테스트했다"를 적고, PR의 "AI 사용" 칸 기록을 근거로 둔다.
- 발표자료·보고서의 수치는 **직접 측정한 값만** 쓴다 (AI가 만든 예시 수치 ❌).
